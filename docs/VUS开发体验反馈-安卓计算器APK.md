# VUS 开发体验反馈 —— 以「安卓计算器 APK」为例

> 对象：VUS 语言作者
> 来源：用 VUS（VUA 组件流）开发安卓计算器 APK（含历史记录、双 ABI、JNI 桥、手工构建链）的完整过程
> 目的：记录开发中感到"不好"的点，附具体现象与改进建议，供作者参考
> （AI 开发从 0 实际体验）

---

## 一、语言 / 运行时层面

### 1.1 全局变量在事件函数内不可用（最痛的点）

现象：编译器全局变量目前有缺陷，事件函数内读写全局变量不可靠，被迫把全部状态放进 VuaSession 状态字典，通过 `界面_取 / 界面_设置` 读写（`calc.vus` 头部专门写了注释规避）。

```vus
#// 状态全部存 VuaSession 状态字典（界面_取 / 界面_设置），
#// 与官方 vua_test.vus 模式一致（编译器全局变量暂有缺陷，事件函数内不使用）。
```

影响：
- 事件函数被迫写成"读字段 → 计算 → 写字段"的显式状态机风格，代码比正常语言啰嗦；
- 新用户第一反应是写全局变量，必然踩坑，且是**静默错误**（无编译错误、无运行时报错，就是变量不生效）。

建议：优先修复；短期至少让编译器对"事件函数内使用全局变量"给出显式报错，而不是静默出错。

### 1.2 字符串标准库操作链繁琐

`calc.vus` 里截断历史记录需要：

```vus
行 = JSON_解析(文本_分割(历史串, "\n"))
# 然后还要 列表_长度、列表_取、转数字(i) 逐个处理
```

一个"按换行拆分字符串"要经过 `文本_分割(返回 JSON 数组字符串) → JSON_解析 → 列表_*` 三层，且长度、下标都要 `转数字` 包裹。字符串处理是脚本语言最高频操作，建议：
- `文本_分割` 直接返回列表（内部已解析），或提供 `文本_行` 之类的一步到位的函数；
- 数组下标/长度允许直接参与算术（编译器自动转），减少 `转数字` 噪音。

### 1.3 `+` 与 `..` 的语义陷阱

纯数字场景 `+` 是算术加法、`..` 是字符串拼接。作者在文档里说明了，但对新用户仍是坑：
- 想拼字符串时用了 `+` → 悄悄变成加法，结果对但类型含义错（如 `"7" + "5"`）；
- 建议至少让 `字符串 + 字符串` 在编译期警告。

### 1.4 事件参数映射是隐式约定

`vua_calc.vua` 里写：

```json
{ "事件": { "事件名": "按数字", "回调变量": ["值=7"] } }
```

渲染树归一化为 `event.collect = ["值=7"]`，Java 端再解析成 `{"值":"7"}` 传给 native，最终落到事件函数参数 `事件_按数字(变量, 值)`。这条链路里：
- `回调变量` 里的键名 `值` 与事件函数形参 `值` 的对应**没有任何校验**；
- 键名写错、函数形参改名、事件名拼错，全部静默失败（界面无反应），调试成本极高。

建议：native 派发事件时校验 collect 键是否与函数形参匹配，不匹配打 elog 告警。

## 二、VUA 组件流 / 渲染协议层面

### 2.1 `.vua` 命名与渲染树命名不一致（直接引发一次线上 bug）

`.vua` 里写的是 `子组件 / 事件 / 回调变量`，渲染树归一化后变成 `children / event / collect`。Java 渲染器为了兼容，每个键都要写 `optX("中文") || optX("英文")` 两套分支。

最典型的坑：`VuaRenderer.collectVars` 原本按"输入控件变量名"读取，而 `.vua` 的按钮事件用的是 `回调变量: ["值=7"]`（字面量参数），导致**按数字键界面毫无反应**，最终靠本地 dump 渲染树才发现两套约定不一致。

建议：
- 在文档（docs/VUA_RENDER_TREE.md）里用一张对照表写死 `.vua 键 ↔ 渲染树键` 的映射，并标注"渲染树是唯一契约"；
- 或者干脆让渲染树保留原键名，只在 `type` 上做归一化，Java 端只认一套键。

### 2.2 渲染树 JSON 是唯一契约，但文档不足

`VuaRenderer.java` 注释里引用了 `docs/VUA_RENDER_TREE.md`，但实际开发中大量行为（eventIndex、collect 归一化、variable 文本 diff）是读代码反推出来的。作者侧建议：
- 提供一个最小参考渲染器（Java/Kotlin 均可），`vus build --apk` 时可以直接带上，开发者不必从零写 View 构建器；
- 渲染树的 JSON Schema（或至少样例 + 字段说明）随 `vus build --apk` 一起生成。

### 2.3 版本号协议（renderHash + screenId）精妙但隐式

用"内容指纹 + 屏序号 + View diff"做增量更新，思路很好。但实际踩了两个坑：
- native 侧漏实现 `vuaRenderHash`，Java 端在运行时才报 `UnsatisfiedLinkError` 崩溃，没有任何中间层兜底；
- 同屏变量更新与换屏重绘两条路径（native 回调 vs Java 本地 `refresh()`）容易触发双重重建，需要 `renderPending` 合并标志这种手写机制。

建议：把指纹/屏序号/重建三者的决策逻辑收敛到 bridge 层统一封装（现在散在 MainActivity / VuaRenderer / VuaBridge 三处）。

## 三、JNI / 工程化层面

### 3.1 JNI 符号手工对齐，编译期零检查

`Java_包名_类名_方法名` 必须与 Java 的 `public static native` 声明逐字匹配，包名一变、方法名一改就运行期崩溃。本次开发中 `com.vus.calc` 包名对齐就修了一轮。

建议：
- `vus build --apk` 从 Java native 声明自动生成 `jni_bridge.c`（而不是手写维护）；
- 或至少提供 `llvm-nm | grep Java_` 的校验脚本，构建后自动核对符号表与 Java 声明一致。

### 3.2 同一份 native 运行时存在两份拷贝，必然分叉

`rt/vua.c`、`rt/libvus_rt.c` 与 `apk/jni/vua.c`、`apk/jni/libvus_rt.c` 各有一份，实测**两副本内容已不一致**。修 bug 时改哪份？构建时编哪份？全靠人脑记忆。

建议：`rt/` 为唯一真源，APK 构建时由脚本同步拷贝（或直接 include 源码路径），并加 hash 校验。

### 3.3 手工构建链非常脆弱

`build.sh` 需要依次正确调用：NDK clang（每个 ABI 一份）→ javac → d8 → aapt → zip → zipalign → apksigner。本次踩到的坑：

| 坑 | 现象 | 原因 |
|---|---|---|
| 新版 JDK | `Unsupported class file major version 69` | javac 25 默认编出 class 69，d8（build-tools 31）只认老版本 |
| 新版 JVM 跑旧 d8 | d8 内部 NPE 崩溃 | 旧 R8 在新 JVM 上运行不兼容 |
| 双 ABI | 两份 .so 路径、staged 结构、zip 内容全要手写对 | 无封装 |

最后是"JDK 8 + `-source 8 -target 8`"绕过的，但这是靠经验试出来的，不是工具链该有的体验。

建议：`vus build --apk` 内置完整构建链（处理 JDK 版本探测与降级），或生成可复现的构建脚本；至少把 d8/JDK 版本兼容性写进文档。

### 3.4 事件回传链路长且无中间校验

`collectVars(Java) → JSON → JNI → vua_dict_from_json → VusDict → handler`，任一层命名不符即静默失败。建议在 `vua_trigger_event` 入口打印事件名 + 参数 JSON（elog），开发者开着 logcat 就能定位。

## 四、调试 / 可观测性层面

1. **无法单测**：Java 渲染器依赖 Android 运行时，native 逻辑只能靠手写 `dump_tree.c` 桌面壳（编译同一份 vua.c/libvus_rt.c，模拟点击后 dump 渲染树）来验证。建议作者侧提供桌面端的 VUA 冒烟测试模板（或直接把 dump_tree 做成 `vus build` 的官方调试子命令）。
2. **错误全静默**：事件名不存在、变量名拼错、collect 键不匹配，界面毫无反应，也没有日志。这是本次开发耗时的最大来源。
3. **路径解析不一致**：`.vua` 文件在桌面端相对 cwd 解析，Android 端相对 filesDir（`vuaSetRootDir`）。同样的 `界面_显示("vua_calc.vua")` 两端行为不同，调试时要记住切换心智模型。

## 五、改进建议（按优先级排序）

1. **修复全局变量**（或在编译期对事件函数内使用全局变量显式报错）—— 这是新用户第一道坎。
2. **渲染树协议文档化 + 最小参考渲染器**，`vus build --apk` 直接附带，消灭"按数字没反应"这类两端约定不一致的 bug。
3. **JNI 桥自动生成**：从 Java native 声明生成 `jni_bridge.c`，构建后自动核对符号。
4. **`vus build --apk` 内置完整构建链**，自动探测/兼容 JDK 版本，支持多 ABI 一次产出。
5. **native 运行时单一真源**（rt/ 唯一，APK 构建时拷贝），杜绝分叉。
6. **事件派发加日志与参数校验**，错误不再静默。
7. **字符串标准库增强**：`文本_分割` 直接返回列表，减少 `转数字 / JSON_解析` 噪音。

## 附：踩坑时间线（本次开发）

1. APK 打包后启动崩溃：`vuaRenderHash` native 方法未实现 → UnsatisfiedLinkError。
2. 修完崩溃后：按数字键界面无反应 → 定位为 Java 端 `collectVars` 与渲染树 `collect:["值=7"]` 约定不一致。
3. 双 ABI 构建：arm64/arm32 各编一份 .so 手工塞进 APK。
4. 环境升级坑：javac 25 → class 69 → d8 不认；旧 d8 在新 JVM 上 NPE。
5. 每次改完都要"本地 dump 验证 + 全量重打包 + 传手机装"，缺少快速反馈回路。
