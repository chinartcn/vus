# 多 AI 协作规范

> 通过多个独立对话框（会话）分工协作，结合 Gitee 的 Issue / 分支 / PR 审查流程，
> 让「写文档」「开发」等角色像真实团队一样协同推进 VUS 项目。
>
> 本文档是**唯一权威分工依据**：所有任务分工必须先写入本文档与对应 Issue，
> 人类只需把 Issue 编号发给对应 AI，AI 自行读取协作。

## 1. 角色定义

| 角色 | 职责 | 交接物 |
|------|------|--------|
| **文档 AI** | 脑暴、设计、写 spec；**兼任代码审查**（相对较闲） | 设计文档 `docs/designs/YYYY-MM-DD-*.md` + 审查意见 |
| **开发 AI**（开发①/开发②…） | 依据设计文档实现代码 | 分支上的代码 + commit + PR |

### 职责边界
- **文档 AI** 只写文档 + 审查代码，不写业务代码（保证审查独立性）。
- **开发 AI** 负责实现，不编写设计规范/文档。
- **铁律：审查者不得审查自己提交的代码。** 文档 AI 不写业务代码，故可独立审查他人提交的代码。
- 同一文件由单一角色负责，避免多对话框冲突。

## 2. 调度与并发约束（执行铁律）

> 以下约束决定了**如何拆任务、何时派发给 AI**，违反会打断其他对话，必须遵守。

### 2.1 并发上限
- **Trae 同时只能进行两个对话框任务**，因此同一时刻最多只有 2 个 AI 在并行工作。
- **一个 AI 完成任务后，才能开启下一个**：当某个角色未开始 / 进行中时，其他后续任务必须排队等待，不得同时铺开。
- 派发时先确认当前哪些 AI 空闲，再分配，避免挤占。

### 2.2 分配时机：开头定死，不中途变更
- **任务一开始就分配好角色与编号，下发后不再改动**。
- 中途改派 / 换人 / 调整职责会打断正在进行的 AI 对话，**禁止**。
- 若确实需要调整，先等当前 AI 交回，再重新分配，并同步更新 Issue。

### 2.3 拆分数量上限
- **轻量级任务：最多拆给 2 个 AI。**
- **重量级任务：尽量控制在 2 个 AI 以内**（匹配并发上限）。
- 无论任务多重，**一次并行派发的 AI 数不得大于 2**；更多子任务按批次排队，前一批交回后再派下一批。

### 2.4 按重要性排序
- 拆出的子任务**按重要性排序**，优先级最高的先派发。
- 排序依据：阻塞后续任务程度 > 影响面 > 工作量。
- 例如：平台适配/编译链（阻塞一切）优先于接口声明，接口优先于生成器映射，最后才是测试。

### 2.5 分工写入 Issue
- 每个任务的分工**详细写入对应 Issue**：角色、编号、职责、交接物、优先级、依赖。
- 人类只需**把 Issue 编号发给对应 AI**，AI 自行读取 Issue 与本文档后开工，无需人类口头转述细节。

### 2.6 防重复分配（文件所有权唯一 + 认领制）【血泪教训】
> 背景：A2/A5 曾同时分给 开发② 与 文档AI，两 AI 各自在隔离环境重复实现，造成返工。
> 根因：任务只按"功能名"命名，没有绑定到**具体文件**，导致多人认领同一处代码。

- **文件所有权唯一**：同一文件在同一时刻**只允许一个 AI 修改**。分工必须显式列出「负责的文件路径」，而非仅功能名。
- **功能级唯一**：同一功能 / 同一段代码**只拆给一个 AI**，禁止拆成多份给多人。
- **认领制**：AI 开工前先在 Issue 评论**认领**（如 `开发② 认领 A2：rt/elog_port.c`）。已认领的文件/功能，其他 AI 不得再碰。
- **分配前先查空**：人类派发前核对 Issue 认领记录，若某文件已被认领，则改派待办的其他文件，避免撞车。
- **文件归属表**：每个子任务必须给出「触碰哪些文件」，作为唯一分配依据。局部冲突时，**优先级高者持有文件，低者改用其他文件或等待**。

#### 当前 EasyLogger 集成的文件归属（示例）
| 文件 | 唯一主人 |
|------|----------|
| `rt/easylogger/`（引入源码） | 开发① |
| `rt/elog_port.c`（A2） | 开发② |
| `rt/libvus_rt.h`（A3） | 文档AI |
| `rt/libvus_rt.c`（A4） | 开发② |
| `src/generator.c`（A5） | 文档AI |
| `Makefile` / `tests/`（B1/B2） | 组织 |

> 结论：A5（`src/generator.c`）只归**一个**主人（文档AI），开发② 不应再实现 A5。

### 2.7 进度透明：每次变更必须提交并推送 Gitee【血泪教训】
> 背景：各 AI 只在本地改了文件、**不提交 Gitee**，导致其他人看不到完成度、
> 无法判断"谁做完了 / 谁没做"，从而重复实现（A2/A5 撞车）。
> 根因：进度只存在于各 AI 本地，未同步到共享仓库。

- **每次完成一项改动，必须立即 `git add` → `commit` → `push` 到 Gitee 对应分支**，禁止只留在本地。
- **进度以 Gitee 分支为准**：判断"是否完成"看分支上是否有该提交，而非听 AI 口头说"我做了"。
- **push 前先 `git pull --rebase`** 拉取他人最新改动，解决冲突后再 push，避免覆盖他人。
- **提交粒度**：一项子任务一个 commit，message 关联 Issue 编号（如 `feat(issue-XX): A2 平台适配`），便于追踪谁做了哪部分。
- **认领 + 提交联动**：认领在 Issue 评论，实现在分支提交，两者都对所有人可见。
- **验收前必须已 push**：合并进主干前，所有涉及文件必须已在共享分支上，禁止拿本地未提交版本当"已完成"。

**正确工作流**：`git pull --rebase`（先同步）→ 实现 → `commit` → `push`（对外可见进度）。
**错误工作流**（禁止）：本地实现 → 不提交 → 口头说"我做完了"。

### 2.8 问题处理：先同步后行动，禁止擅自行动【铁律】
> 用户明确要求：凡是出现问题的，先通过 Issue 与所有相关 AI 同步状态，**最终确认后**再执行，**不得擅自行动**。

- **发现问题时，第一动作是"同步"，不是"修复"**：
  1. 在 Issue 评论里**描述问题**（现象、影响文件、是否已 push、是否与别人冲突）。
  2. **@ 到相关 AI**，等待对方确认状态（是否已认领 / 已在实现 / 已有权威版本）。
  3. 确认无冲突、分工明确后，**再执行**修复/回滚/提交。
- **禁止擅自行动**：不得在未与他人同步、未确认归属的情况下，自行覆盖文件、回滚他人改动、重复实现或直接 push 与别人冲突的版本。
- **冲突优先走 Issue 仲裁**：多个 AI 改了同一文件时，先在 Issue 说明各自改动，由人类或指定角色裁定，禁止抢着 push 覆盖。
- **"确认"的标准**：相关 AI 在 Issue 明确回复同意，或人类拍板。单方口头"我觉得没问题"不算确认。
- **例外**：仅改动自己唯一拥有的文件、且不与他人耦合时，可先 commit 到自己的分支，但 push 前仍需在 Issue 说明，避免冲突。

### 2.9 提交完整性：提交前验证依赖齐全【血泪教训】
> 背景：主会话提交 `generator.c` 时**漏提交其依赖的 `src/ast.h`**（`VusAstDictLiteral.values` 字段），
> 本地编译通过（本地有未提交的 ast.h），push 后开发② 拉取**编译失败**。
> 根因：只提交"手头改的文件"，没把"它所依赖的同批改动"一并提交。

- **提交前必须 `make clean && make` 全量重编**，确认干净状态能编译（而非依赖工作区残留的未提交改动）。
- **检查依赖完整性**：提交某文件前，确认它引用的结构体 / 函数定义（可能在别的 `.h` / `.c`）已提交或随本提交一起提交。
- **提交清单自查**：`git status` 中同一功能相关的 untracked / modified 文件是否都 add。**相互依赖的文件必须同一次提交**，禁止只提交一半。
- **提交后验他人视角**：有条件时用干净克隆（或 `git stash` 其他改动后）`make` 验证，确保别人 pull 后能编译。

## 3. Gitee 协作流程

```
新想法
  └→ 创建 Issue（文档 AI 或 人类），并在 Issue 内写明完整分工
  └→ 【文档 AI】设计阶段：产出 docs/designs/ 设计文档，提交到分支
  └→ 【开发 AI】按 Issue 分工并行实现（并发 ≤2），基于设计文档写代码，提交到各自分支
        └→ 前一批交回后，再派下一批（若子任务 >2）
  └→ 发起 PR
  └→ 【文档 AI】PR 审查（代码质量 + brooks-lint，审查他人提交的代码）
        ├─ 通过   → 合并 → 关闭 Issue
        └─ 不通过 → 打回对应角色修改后重新审查
```

### 3.1 PR 审批与合并（含阻塞处理）【复盘补充】
> 背景：EasyLogger 合并时 PR 配置了审查者(assignees)与测试者(testers)，合并报 405「未通过测试」。
> 根因：① 文档AI 在 Issue 口头"审查通过"≠ Gitee PR 的 assignee approve（需单独操作）；
> ② 测试者无 API 审批入口，需界面操作，导致合并阻塞。

- **"审查通过"分两层，缺一不可**：
  1. **内容审查**：文档AI 在 Issue / PR 评论确认代码质量（口头/评论）。
  2. **Gitee 审批**：assignee 在 PR 上 `approve`（可用 `manage_pull_review approve`），testers 通过或 `testers_number=0`。
- **创建 PR 时明确审批设定**：指明审查者与测试者；若无独立测试环节，`testers_number` 设为 `0`，避免合并被测试审批卡住。
- **合并报 405「未通过测试」的处理**：先看 PR 详情中 assignees/testers 的 `accept` 状态；`accept=false` 者需先 approve；测试者无 API 时，将 `testers_number` 降为 `0` 解除后重试合并。
- **合并方式**：按需选 `merge` / `squash` / `rebase`；合并时可 `prune_source_branch` 清理源分支、`close_related_issue` 关闭关联 Issue。

## 4. 分支与提交规范

- 每个 Issue 建一个分支，命名：`feature/issue-<编号>-<简述>`。
- 多个角色并行时，在分支名后加角色标记区分，如 `feature/issue-3-日志功能-dev`。
- commit message 关联 Issue 编号，便于追溯。
- 审查未通过不得合并。

## 5. 决策权

- **人类为最终拍板者**，负责：创建/编号 Issue、派发（发编号给对应 AI）、裁定冲突。
- 文档 AI 作为审查者给意见，是否采纳由人类或开发角色判断。
