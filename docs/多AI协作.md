# 多 AI 协作规范

> 通过多个独立对话框（会话）分工协作，结合 Gitee 的 Issue / 分支 / PR 审查流程，
> 让「写文档」「协助开发」「审查」三种角色像真实团队一样协同推进 VUS 项目。

## 1. 角色定义

| 角色 | 职责 | 交接物 |
|------|------|--------|
| **文档 AI** | 脑暴、设计、写 spec | 设计文档 `docs/designs/YYYY-MM-DD-*.md` |
| **开发 AI** | 依据设计文档实现代码 | 分支上的代码 + commit + PR |
| **审查 AI** | 审查设计/代码（含 brooks-lint） | PR Review 意见 |

### 单一职责边界
- 文档 AI 不修改业务代码。
- 开发 AI 不编写设计规范/文档。
- 审查 AI 只提意见，不直接改代码。
- 避免多个对话框在同一文件上互相冲突；同一文件由单一角色负责。

## 2. Gitee 协作流程

```
新想法
  └→ 创建 Issue（文档 AI 或 人类）
  └→ 【文档 AI】设计阶段：产出 docs/designs/ 设计文档，提交到分支
  └→ 【开发 AI】实现阶段：基于设计文档写代码，提交到同一分支
  └→ 发起 PR
  └→ 【审查 AI】PR 审查（代码质量 + brooks-lint）
        ├─ 通过   → 合并 → 关闭 Issue
        └─ 不通过 → 打回对应角色修改后重新审查
```

## 3. 分支与提交规范

- 每个 Issue 建一个分支，命名：`feature/issue-<编号>-<简述>`。
- commit message 关联 Issue 编号，便于追溯。
- 审查未通过不得合并。

## 4. 决策权

- **人类为最终拍板者**。
- 审查 AI 只给意见，不强制；是否采纳由人类或开发 AI 判断。

## 5. 交接与验收

- 每个角色完成其交接物后，通知下一个角色（通过 Issue 评论 / PR 备注 / 对话框接力）。
- 合并前需满足：设计文档已入库、代码通过审查、测试通过。
