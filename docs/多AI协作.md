# 多 AI 协作规范

> 通过多个独立对话框（会话）分工协作，结合 Gitee 的 Issue / 分支 / PR 审查流程，
> 让「写文档」「开发」「审查」三种角色像真实团队一样协同推进 VUS 项目。
>
> **调整原则**：开发是瓶颈，审查 AI 也参与开发以提速；审查职责移交给较闲的文档 AI。

## 1. 角色定义

| 角色 | 职责 | 交接物 |
|------|------|--------|
| **文档 AI** | 脑暴、设计、写 spec；**兼任代码审查**（因较闲） | 设计文档 `docs/designs/YYYY-MM-DD-*.md` + 审查意见 |
| **开发 AI** | 依据设计文档实现代码 | 分支上的代码 + commit + PR |
| **审查 AI** | **开发为主**（吸收实现能力，分摊开发任务） | 分支上的代码 + commit + PR |

### 职责边界
- **文档 AI** 只写文档 + 审查代码，不写业务代码（保证审查独立性）。
- **开发 AI** 负责实现，不编写设计规范/文档。
- **审查 AI** 以开发为主，不写设计规范/文档。
- **铁律：审查者不得审查自己提交的代码。** 文档 AI 不写业务代码，故可独立审查他人提交的代码。
- 同一文件由单一角色负责，避免多对话框冲突。

## 2. Gitee 协作流程

```
新想法
  └→ 创建 Issue（文档 AI 或 人类）
  └→ 【文档 AI】设计阶段：产出 docs/designs/ 设计文档，提交到分支
  └→ 【开发 AI】【审查 AI】并行实现：基于设计文档写代码，提交到各自分支
  └→ 发起 PR
  └→ 【文档 AI】PR 审查（代码质量 + brooks-lint，审查他人提交的代码）
        ├─ 通过   → 合并 → 关闭 Issue
        └─ 不通过 → 打回对应角色修改后重新审查
```

> 说明：开发 AI 与审查 AI 可并行承担不同任务；它们提交的 PR 统一由文档 AI 审查。

## 3. 分支与提交规范

- 每个 Issue 建一个分支，命名：`feature/issue-<编号>-<简述>`。
- 多个角色并行时，可在分支名后加角色标记便于区分，如 `feature/issue-3-日志功能-dev`、`feature/issue-3-日志功能-reviewer`。
- commit message 关联 Issue 编号，便于追溯。
- 审查未通过不得合并。

## 4. 决策权

- **人类为最终拍板者**。
- 文档 AI 作为审查者给意见，是否采纳由人类或开发角色判断。

## 5. 交接与验收

- 每个角色完成其交接物后，通知下一个角色（通过 Issue 评论 / PR 备注 / 对话框接力）。
- 合并前需满足：设计文档已入库、代码通过审查、测试通过。
