# 多 AI 协作 · 消息转发规范

> 你（人类）是多 AI 协作的**唯一枢纽**：所有 AI 对话框只有你能同时看到。
> AI 之间**不能直接对话**，只能通过两种方式交换消息：
> ① **Gitee Issue 评论**（异步、持久、所有人可见）
> ② **你口头转发**（在对话框之间复制粘贴）
>
> 本文档教你**怎么规范地转发消息**，避免"搞懵、漏传、重复、冲突"。

---

## 1. 你为什么搞懵（根源）

- 多个 AI 对话框各自独立，各说各话，你夹在中间。
- 消息散落各处：A 的进度在 Issue、B 的疑问在对话框、C 的评论没人看。
- 你靠记忆转发，容易漏、容易传错、容易把一个功能发给两个 AI 做。

**核心解法一句话：所有消息都落到 Issue，你只做"发编号 + 转发链接"，不做口头转述。**

---

## 2. 协作拓扑（谁和谁能说话）

```
                    ┌──────────────┐
                    │  你（人类）  │  ← 唯一枢纽，看得见所有对话框
                    └──────┬───────┘
         ┌─────────────────┼──────────────────┐
         │  发编号/链接     │  发编号/链接       │  发编号/链接
         ▼                 ▼                  ▼
   ┌──────────┐     ┌──────────┐      ┌──────────┐
   │ 文档AI   │     │ 开发①    │      │ 开发②    │
   └────┬─────┘     └────┬─────┘      └────┬─────┘
        └─────────── 通过 Gitee Issue 评论 ────┘
                    （AI 之间唯一的共同会话区）
```

- **AI ↔ 你**：通过对话框（你读它的输出、发指令）。
- **AI ↔ AI**：只能通过 **Gitee Issue 评论**。AI 不会主动看，需要你**在对话框里把 Issue 链接发给对方**，或**把对方的评论转发过去**。

---

## 3. 铁律：一切以 Issue 为准

1. **所有**分工、进度、问题、确认，**先写进 Issue**，再考虑口头转发。
2. 你只转发**编号 + 链接**，让 AI 自己去 Read Issue，**不要口头复述细节**（复述会丢信息、易传错）。
3. 判断"谁做完了"，看 **Gitee 分支/Issue 勾选**，不信"口头说做完了"（见协作文档 2.7）。
4. 出问题：先在 Issue 同步，**等确认再执行**，禁止擅自行动（见协作文档 2.8）。

---

## 4. 消息类型与怎么转发

| 消息类型 | 发给谁 | 怎么写/转发 | 落点 |
|----------|--------|-------------|------|
| **派发任务** | 对应 AI | 只发 Issue 编号 + 一句话指令 | Issue body 分工表 |
| **状态同步** | 所有相关 AI | 在 Issue 评论一段状态，再转发链接 | Issue 评论 |
| **问题上报** | 相关 AI + 你 | AI 在 Issue 评论描述问题，你转发并 @ 确认 | Issue 评论 |
| **确认/拍板** | 对应 AI | 你在 Issue 评论明确"确认某某执行"，再发链接 | Issue 评论 |
| **审查请求** | 文档AI | 把 PR 链接发给文档AI | PR |
| **已完成通知** | 你 | AI 完成 → 你转发下一位接手 | Issue 评论 |

---

## 5. 人类操作手册（四步）

### 第一步：开工前，把分工写进 Issue body
- 每个子任务一行：`编号 | 角色 | 优先级 | 状态 | 负责文件 | 职责`。
- 明确**文件归属**（同一文件只归一个 AI），防止重复实现。

### 第二步：派发 = 只发编号
- 对开发② 说：`Issue #IK907N，你做 A2，读 Issue 分工后开工。`
- 不要复述需求细节，让它自己读。

### 第三步：AI 回复后 = 转发链接
- AI 在对话框给了结论，你把它**写进 Issue 评论**（或让它在 Issue 评论），然后：
  - 需另一 AI 接手 → 把 Issue 链接发给它。
  - 需你确认 → 你在 Issue 评论 `确认执行`，再把链接发回给该 AI。

### 第四步：冲突/问题 = 回 Issue 仲裁
- 多 AI 改了同一文件 → 让大家都在 Issue 说清各自改动，你（或指定角色）裁定，**禁止抢 push**。

## 6. 常用消息模板（复制即用）

**派发任务：**
> 请读 Issue #IK907N，你负责 [A2]，按分工表中的文件归属实现，完成后提交并推送 Gitee，勿擅自扩大范围。

**转发状态给另一 AI：**
> 请读 Issue #IK907N 最新评论：[链接]。文档AI 已确认 A3/A5，你接 A2，注意 [src/generator.c] 唯一主人是文档AI，别重复改。

**请求确认：**
> 请读 Issue #IK907N：主会话已建分支并发起 PR #1 [链接]，请文档AI 审查，通过后合入。

**同步问题：**
> 请读 Issue #IK907N：开发② 报告 [编译失败]，已定位根因 [漏提交 ast.h]，分工方案B已确认，主会话执行中。

## 7. 角色 / 文件归属速查表

| 角色 | 职责 | 负责文件示例 |
|------|------|--------------|
| **文档AI** | 设计、写 spec、**代码审查** | `docs/designs/*.md`、审查任何他人代码 |
| **开发①** | 实现 | 如 `rt/easylogger/`（源码引入） |
| **开发②** | 实现 | 如 `rt/elog_port.c`、`rt/libvus_rt.c` |
| **组织/主会话** | 编译链、测试、建分支 PR | `Makefile`、`tests/` |

> 规则：**审查者不审查自己代码**；同一文件同一时刻只有一个主人。

---

## 8. 标准流程示例（EasyLogger 实际走法，供对照）

```
① 你建 Issue IK907N，分工表写清 A1-A5 + 文件归属
② 你发编号给各 AI：开发①→A1，开发②→A2/A4，文档AI→A3/A5
③ 各 AI 完成 → 各自提交推送 Gitee（不是只留本地）
④ 若发现重复/冲突 → 大家回 Issue 评论说明，你裁定
⑤ 你确认后，主会话建分支、发 PR，把 PR 链接发给文档AI
⑥ 文档AI 审查 → 通过 → 合入 → 关闭 Issue
```

**你每次只做一件事：把"Issue 编号 / 链接"发到该发给的对话框，并让讨论发生在 Issue 里。**
