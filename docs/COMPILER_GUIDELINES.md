# VUS 编译器开发指南

> 参考自 Ferret 编译器设计理念，结合 VUS 语言特性定制

## 核心原则

1. **架构先行，拒绝玩具**：不要为了快速实现而搭建"基础版"临时架构。解析、语义分析、代码生成等核心子系统，应先设计好正确的边界和数据模型，即使某些功能暂时不完善。

2. **不盲从，只借鉴**：参考其他编译器设计时，理解其背后的思路，而不是照搬代码。只实现当前需要的部分，避免过早的过度设计。

3. **明确优先级**：正确性 > 语义清晰性 > 可维护性 > 诊断质量 > 性能。

4. **小步快跑，易于审查**：每个提交只做一件事，保持提交规模小、聚焦。

## 编码规范

### C 语言规范（编译器核心）

- **内存管理**：正确分配与释放，避免泄漏。所有 `malloc` 必须有对应的 `free`。
- **指针使用**：正确初始化与检查，避免悬空指针。函数参数中的输出指针必须标注 `/* out */`。
- **错误处理**：检查系统调用和库函数的返回值。错误信息通过 `VusError` 链传递。
- **命名规范**：
  - 类型名：`VusXxx` 驼峰命名（如 `VusToken`、`VusAstNode`）
  - 函数名：`vus_xxx_yyy` 蛇形命名（如 `vus_lexer_tokenize`）
  - 常量/宏：`VUS_XXX_YYY` 全大写（如 `VUS_TOKEN_EOF`）
- **文件结构**：每个源文件头部应有描述其用途的文件头注释。
- **头文件保护**：使用 `#ifndef VUS_XXX_H` / `#define VUS_XXX_H` 保护。

### Python 规范（构建脚本/测试工具）

- 遵循 PEP 8，缩进使用 4 个空格。
- 使用类型提示（Type Hints）。
- 使用 `snake_case` 命名函数和变量。

## 架构设计

### 编译器流水线

```
VUS 源码 (.vus)
    ↓
[词法分析器] → Token 流
    ↓
[语法分析器] → AST
    ↓
[语义分析器] → 带类型信息的 AST
    ↓
[C 代码生成器] → .c 文件
    ↓
[GCC] → 可执行文件
```

### 阶段划分

| 阶段 | 输入 | 输出 | 职责 |
|------|------|------|------|
| 词法分析 | 源码字符串 | Token 流 | 分词、关键字识别、注释/空白过滤 |
| 语法分析 | Token 流 | AST | 递归下降解析、语法错误检测 |
| 语义分析 | AST | 带类型信息的 AST | 类型检查、符号表构建、循环依赖检测 |
| 代码生成 | AST | C 源码 | 生成合法的 C 代码、插入引用计数 |

## 测试策略

1. **测试驱动开发**：在修复 Bug 或添加新功能前，先写一个能复现问题的测试用例。
2. **三层次测试**：
   - 单元测试：测试单个组件（词法分析、语法分析）
   - 集成测试：测试完整编译流水线
   - 端到端测试：编译并运行 VUS 程序，验证输出
3. **测试目录结构**：`tests/` 目录下按阶段组织测试文件。
